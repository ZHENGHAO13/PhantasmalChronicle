# PhantasmalChronicle 开发工作流

> 适用项目：Minecraft Forge 1.20.1 / `phantasmbriefing`
>
> 目标：任何后续修改都以“兼容旧内容、模块化、低冗余、多人服务器稳定、素材易扩展”为第一约束。本文是后续修改的强制工作流，不是建议清单。

## 1. 唯一源码基线

1. 每次开发必须从用户最新确认、最新实际运行的完整源码开始。
2. 禁止从历史补丁、旧 ZIP、旧版 `PhantasmMaker-.html`、旧聊天中的单个文件反向覆盖当前源码。
3. 开始修改前必须确认：
   - 当前 `src/main/java`；
   - 当前 `src/main/resources`；
   - 当前网页编辑器版本（如果本次涉及网页）；
   - 当前数据格式版本和网络协议版本。
4. 大修改先复制工作目录并保存检查点，不能在唯一基线上连续无回退地修改。

### 为什么必须这样做

曾发生过“新增 NPC 逐字音效模块时误用了旧网页基线”，导致新版对话 `contents` 被旧 `lines` 编辑逻辑覆盖。今后任何功能合并都必须以最新完整版本为源，不允许用旧模块覆盖新模块。

---

## 2. 每次开发前的强制风险分析

开始编写前先写至少两个：

- `自问：最可能破坏什么？答：……`
- `自问：旧内容/多人/热加载可能受什么影响？答：……`

然后列出影响面：

- Java 数据解析
- 玩家存档 NBT
- 网络包
- 客户端 UI
- 服务端逻辑
- NPC 实体
- 热加载
- 网页编辑器
- 模组资源（图片、声音、模型、语言）
- 外部兼容（FTB Quests、Explorer's Compass 等）
- 公共 API / Forge Event / Mixin

只有确认影响面后才开始改。

---

## 3. 模块化原则

### 3.1 一个模块只负责一类职责

当前建议边界：

- `data/`：JSON 数据模型、旧格式兼容解析、数据管理器。
- `service/`：服务端/公共业务逻辑。
- `client/`：纯客户端状态、HUD、渲染、声音。
- `client/screen/`：界面。
- `dialogue/sound/`：NPC 逐字音效定义与注册元数据。
- `network/packet/`：数据包 DTO、编码、解码、入口。
- `event/`：Forge 事件桥接，只做事件转发和轻量调度。
- `integration/`：第三方模组兼容。
- `api/`：明确允许其他模组依赖的公共扩展接口。
- `util/`：真正无业务状态的通用小工具。

### 3.2 禁止“大万能类”继续膨胀

新增功能时先问：

> 这是 `QuestRuntimeService` / `BriefingPlayerData` 已有职责，还是应该进入独立子模块？

原则：

- 对外入口可以稳定；
- 内部实现拆模块；
- 不为了“文件少”把所有代码堆回一个类；
- 也不为了“模块化”制造大量只有十几行、没有独立职责的小文件。

### 3.3 禁止复制已有业务逻辑

编写前必须搜索：

- 是否已经存在相同判断；
- 是否已经有 API/service；
- 是否已经有资源注册器；
- 是否已经有条件/动作解析器。

例如：

- 活跃阶段统一由任务运行时逻辑判断；
- 活跃目标统一复用顺序/自由目标规则；
- NPC 安全落点统一由 `NpcSpawnPlacementService` 负责；
- 对话逐字音效统一由 `DialogueVoiceRegistry` + `DialogueTypewriterSoundPlayer` 负责；
- JSON 通用兼容解析优先放 `JsonDataUtil`，禁止每个 Spec 自己复制 `sanitize/readActions/readText`。

## 4. 冗余代码与文件清理规则

每次较大修改完成后必须检查：

1. 完全相同文件；
2. 没有任何调用、注册、反射、Mixin、Forge Event 入口的类；
3. 无调用的 private 方法；
4. 无用 import；
5. 被新系统取代的旧 Screen / Packet / Widget / Helper；
6. 临时调试类、临时日志、临时命令；
7. 已删除界面遗留的语言键、模型、声音或贴图；
8. 两套平行实现同一功能的旧链路。

### 不能用“无显式引用 = 删除”

以下类型即使没有普通 Java 调用也可能必须保留：

- `@Mod.EventBusSubscriber`
- `@SubscribeEvent`
- Mixin
- 注册器入口
- 网络包注册入口
- Forge 自动发现的能力/事件
- `api/` 下明确公开的扩展点
- 旧存档/旧 JSON 兼容入口

删除前必须确认运行入口。

### 允许保留的“看似冗余”内容

只有两类：

1. 仍然承担旧格式/旧存档兼容；
2. 用户已经明确要求为未来功能预留的公共 API / 扩展接口。

应在代码注释或工作记录中写明保留原因，避免以后被再次误删。

---

## 5. 全旧内容兼容原则

**不能只兼容本次修改的类型。** 每次数据格式变化都要检查整个内容体系。

核心规则：

> 读取旧格式 → 内存中规范化为当前模型 → 运行为当前模型 → 保存时写当前格式。

网页编辑器不得因为“不认识旧字段”就把旧内容写成空值。

### 5.1 对话

必须兼容：

- 当前 `contents`（文字/图片混排）；
- 旧 `lines`；
- 更旧 `text`；
- `choices` / `options`；
- 旧 action 名称，如 `close`、`open_trade`、`give`；
- 旧 `targetId` 与新的结构化 `questId/phaseId/objectiveId`；
- 旧文本对象 `{value}` / `{text}` / `{key}`；
- 旧 presentation 字段作为序列化兼容信息。

不能再次把 `contents` 保存回空 `lines`。

### 5.2 任务 / 阶段 / 目标

必须保留：

- 旧任务无阶段格式；
- 旧 `requiredQuestId` / parent 关系；
- 顺序阶段与自由阶段；
- 顺序目标与自由目标；
- 历史模式别名：`parallel / non_linear / nonlinear / any_order`；
- 旧 objective 文本、目标类型别名、提示类型别名；
- 旧玩家阶段/目标进度的 NBT 迁移或兼容读取。

当前前置类型：

- 整个任务完成；
- 指定任务阶段完成；
- FTB 任务完成。

不要重新加入“指定阶段目标完成”作为任务前置，除非用户以后明确恢复。

### 5.3 旅者手册 / 旧图片教程

必须兼容：

- 旧平铺 `pages`；
- 新分组/lesson；
- 旧 `visibility`；
- 当前永久 `unlock`；
- 旧教程任务仍可通过兼容 UI/数据读取继续工作。

手册的阶段/目标解锁一旦发生，要写入玩家存档永久保持，不应因当前任务状态变化重新锁回去。

### 5.4 NPC

必须兼容：

- `bindingId` 与旧 `id`；
- 旧单个 `questId` 与当前 `questIds`；
- 旧单个 `spawn` 与当前 `spawns`；
- 旧 offset 数组和当前 XYZ；
- 已生成实体保存的 Binding ID；
- 热加载后旧实体必须重新读取最新 Binding，而不是要求重新生成；
- 旧 NPC 没有逐字音效字段时，默认使用模组默认声音。

### 5.5 商店 / 交易 / 钱包

数据管理器可以共用底层 JSON 加载框架，但业务入口保持独立。旧 ID、名称、扁平条目、旧 item/result 表达必须继续兼容，不能为了减少文件数把不同业务模型强行合并。

---

## 6. 网页编辑器防回退规则

如果修改 `PhantasmMaker-.html`：

1. 必须从最新功能完整版本开始；
2. 修改前记录当前已有功能；
3. 修改后检查这些功能没有消失；
4. 对旧 JSON 做读取测试；
5. 再写出并重新读取一次，检查数据没有丢失；
6. `node --check` 必须通过；
7. “检查并写入”涉及旧格式迁移时应先备份旧内容。

重点回归：

- 图文混合对话；
- 自动入口场景；
- 保持在最底层；
- 玩家选项气泡；
- NPC 对话绑定；
- NPC 结构生成；
- NPC 逐字音效选择；
- 任务阶段/阶段前置；
- 手册永久解锁条件；
- 商店/交易/钱包。

---

## 7. NPC 对话与气泡规则

- 对话入口按优先级匹配；无条件兜底节点应保持在最后。
- “保持在最底层”是实际运行顺序，不只是网页视觉排序。
- 对话开始后，第一视角抬头查看图片不能因为准星离开 NPC 就把气泡关闭。
- 图片内容保持比例缩放，不拉伸、不裁切；图片页不触发逐字声音。
- 玩家选项不是 NPC 台词，不触发 NPC 逐字声音。
- 跳过逐字动画时不补播剩余字符音效。

---

## 8. NPC 结构生成规则

NPC 生成是多人服务器敏感逻辑，必须：

- 不做无限重试；
- 同一结构同一次扫描去重；
- 失败有冷却，不刷 WARN；
- 自动寻找安全地面时验证：脚部、头部、脚下支撑、液体、实体完整碰撞箱；
- 不勾选安全地面时严格使用结构锚点 + XYZ 偏移，碰撞则不生成；
- 高度图结果不能直接当作最终可站坐标，必须做最终碰撞验证；
- 热加载后已经生成的剧情 NPC 应更新 Binding，而不是强制玩家删除重生。

临时碰撞诊断日志只能在定位故障时加入，问题解决后必须删除。

---

## 9. NPC 逐字音效模块

用户不能通过网页上传音频。只能选择模组随包提供的内置音效。

当前模块：

- `dialogue/sound/DialogueVoiceDefinition`
- `dialogue/sound/DialogueVoiceRegistry`
- `registry/ModSounds`
- `client/DialogueTypewriterSoundPlayer`
- `data/NpcTypewriterSoundSpec`
- `service/NpcDialogueVoiceService`

### 手动新增一个逐字音效

开发者添加新声音时只需要触碰声音资源/注册层，禁止改 NPC、对话、网络和网页业务代码。

1. 放入：
   `src/main/resources/assets/phantasmbriefing/sounds/<name>.ogg`
2. 在：
   `src/main/resources/assets/phantasmbriefing/sounds.json`
   增加 SoundEvent 映射。
3. 在：
   `DialogueVoiceRegistry`
   增加一条 `DialogueVoiceDefinition`。
4. 重新编译。网页“刷新资源”后自动读取新的音效选项。

推荐音频规范：

- OGG Vorbis；
- Mono；
- 44.1 kHz 或 48 kHz；
- 推荐 30–100 ms；
- 尽量不超过 200–250 ms；
- 避免过长尾音，否则逐字播放会叠音。

当前资源包括默认逐字音效与村民逐字音效。

### 多人性能规则

逐字显示和逐字声音必须完全客户端本地执行：

- 服务端只在打开对话时发送一次 voice ID + volume；
- 禁止每个字符发一个网络包；
- 禁止服务器每个字符广播声音；
- 客户端只播放自己当前会话的声音。

## 10. 素材扩展设计原则

新增任何“以后可能会有多份”的素材，都优先设计为：

> 资源文件 + 中央注册/清单 + 动态编辑器列表

而不是：

> 每加一个素材就在多个 Screen / Packet / NPC 类里写一个 if。

适用对象：

- NPC 逐字音效；
- GUI 主题资源；
- 任务/手册图片类型；
- 后续 NPC 表情/气泡样式；
- 后续 VFX 预设。

素材 ID 必须稳定。文件名可以以后调整，但旧 JSON 里保存的逻辑 ID 尽量不要变化。

---

## 11. 网络协议规则

任何修改以下内容都要检查网络协议：

- Packet 注册数量/顺序；
- 编码字段顺序；
- 字段类型；
- 客户端/服务端共同读取的数据结构。

如果协议不兼容，必须提升 `ModNetwork` 协议版本。

不要出现：

> Java 编译没问题，但客户端和服务器包序列化顺序不同。

---

## 12. 玩家可见文字规则

新增加或修改的 Minecraft 玩家可见 Java 文本：

- 使用翻译键；
- 同步更新 `zh_cn.json` 和 `en_us.json`；
- 颜色只放在语言文件中；
- 中文颜色使用 Minecraft `§` 代码；
- 不使用 `§8` / `§7`。

网页编辑器自己的文本不属于 Minecraft Java 玩家文本，可以使用网页 I18N。

删除旧 Screen / Widget 后，要同步删除确定不再使用的语言键，不能留下资源垃圾。

---

## 13. 性能规则（多人服优先）

服务端高频逻辑必须优先优化：

- NPC 提示扫描；
- 任务自动检查；
- 结构 NPC 检查；
- 实体目标判断。

原则：

- 能事件驱动就不每 Tick 全扫描；
- 能缓存就不重复解析；
- 玩家移动/背包变化等状态变化时再检查；
- 大范围实体/区块扫描必须限频和限范围；
- 失败重试必须有限次数 + 冷却；
- 客户端 UI/VFX/声音不把逐帧结果同步到服务器。

---

## 14. 调试规则

允许为了定位问题临时加入：

- 详细日志；
- 临时诊断字段；
- 临时测试命令。

但必须满足：

1. 日志限频，不能刷屏；
2. 能输出直接证据，例如方块 ID、实体 ID、AABB、坐标；
3. 问题定位并修复后删除临时诊断代码；
4. 正式版本不得保留无调用的 `*Diagnostics`、临时 `System.out`、`printStackTrace`。

## 15. 每次交付前的强制检查

### Java / 架构

- [ ] 搜索被删除类的残留引用。
- [ ] 搜索完全重复文件。
- [ ] 搜索无引用顶级类，并区分 Forge/Mixin/API 自动入口。
- [ ] 搜索无调用 private 方法。
- [ ] 搜索无用 import。
- [ ] 搜索临时调试日志/类。
- [ ] 检查是否出现两套实现同一业务逻辑。
- [ ] 检查大类是否因为本次功能继续膨胀；必要时拆模块。

### 数据兼容

- [ ] 当前格式能读取。
- [ ] 至少上一代格式能读取。
- [ ] 已知更老别名/字段能读取。
- [ ] 读旧 → 写新 → 再读，核心内容不丢失。
- [ ] 玩家旧 NBT 不被清空。

### 资源

- [ ] 所有 JSON 可解析。
- [ ] `sounds.json` 中声音文件实际存在。
- [ ] 所有内置 Dialogue Voice 在 `sounds.json` 有对应事件。
- [ ] OGG 可以被正常解码。
- [ ] 模型引用的文件存在。
- [ ] `zh_cn` / `en_us` 键一致。
- [ ] 删除已确认不用的语言键/资源。

### 网页（如果修改）

- [ ] `node --check` 通过。
- [ ] 使用最新完整网页基线。
- [ ] 旧 JSON 导入不丢内容。
- [ ] 检查并写入不把未知/旧内容变空。

### 编译

- [ ] 有完整 Gradle 环境时执行 `compileJava`/必要的 `runClient`。
- [ ] 如果环境无法完整 Forge 编译，只能报告已经做过的静态/语法/资源检查；禁止宣称“完整编译通过”。
- [ ] 用户给出实际 Gradle 编译日志时，以日志错误为最高优先级修复。

## 16. 交付规则

默认规则：

- 小改：只打包本次新增/修改文件，保持原目录结构；
- 有删除：单独告诉用户删除路径；
- 不把没变的文件塞进普通补丁。

例外：

- 用户明确说“我会删除旧 src，给我完整替换包”时，必须提供完整 `src`。

完整替换包的 ZIP 根目录应直接包含：

```text
src/
```

不能再套一层莫名其妙的工程目录。

大型任务应保留阶段检查点，但最终只给用户明确的一份正式交付包，避免多个相互覆盖的候选包。

已经清理的旧平行链路包括：

- 旧独立 Traveler Manual Screen；

- 旧 Tutorial 兼容链；

- Mixin；
- `api/` 下扩展点；

这一区分以后必须继续遵守。

## 18. 后续开发的一句话流程

> **最新完整基线 → 风险/影响面 → 查现有模块 → 设计扩展点 → 编写 → 旧格式迁移测试 → 多人性能检查 → 冗余扫描 → 资源检查 → 编译/语法检查 → 按用户要求打包。**
